## 結論から

ブラウザ完結の画像変換SaaS **quickconv**(HEIC→JPG、WebP→PNG など)を約4ヶ月運用し、直近30日の計測データに基づいて **「維持運転」(メンテナンスモード)に降格** しました。

30日の実測はこうです。

| 指標 | 実測(2026-06-06 〜 07-04) |
|---|---|
| 週間PV(pv7d) | 751〜1,091 で横ばい |
| 検索流入(7日間) | 最大25 → **最終週 1** |
| MRR(月間経常収益) | **¥0**(変動なし) |
| 有料購読者 | **0人**(変動なし) |
| 維持費 | ドメイン代 約$9/年 のみ |

「もう少し続ければ伸びるかも」を封じるため、撤退判断そのものを機械化しました。この記事では、実データを全部出した上で、**効いたこと3つ / 無駄だったこと3つ** に絞って書きます。

## quickconv とは

- iPhone の HEIC 画像を JPG に、WebP を PNG に、といった形式変換をブラウザ内で完結させる無料ツール
- 2026-03-10 に最初のコミット、4月上旬にローンチ
- 技術構成は Cloudflare 上のサーバーレス(pnpm monorepo + turbo + sharp + workerd)。ランニングコストはドメイン代のみ
- 変換処理はブラウザ内で行うため、サーバー費用がほぼゼロ(技術構成の詳細は別記事にします)

フルスタックエンジニアの個人開発としては「作る」工程は順調でした。問題はその後です。

|---|---|---|---|---|---|
| 06-07 | 864 | 15 | 313 | 42 | ¥0 |
| 06-09 | 1,091 | 21 | 314 | 43 | ¥0 |

週間PVは1,000前後で安定して見えます。しかし最終週のアクセス上位パスを見ると実態が分かります。

```
/              39
/api/account   33
/robots.txt    29
/wp-ws68.php   20   ← WordPress脆弱性スキャン(quickconvはWordPressではない)
/phpinfo       14   ← 同上
/u30.php       12   ← 同上
```

**PVの中身のかなりの部分は、人間ではなく脆弱性スキャンのボットでした。** 「PVが横ばいだからまだ望みがある」ではなく、「人間の訪問はさらに少ない」が正しい読みです。検索流入が 25→1 に落ちた事実と合わせて、成長シナリオは棄却しました。

## 効いたこと 3つ

### 1. KPI計測を自動化して、数字から目を逸らせなくした

毎朝、PV・流入元・Stripe の MRR・購読者数を自動でスナップショットしました。個人開発では「ダッシュボードを見に行かない自由」があるせいで、感触だけで延命しがちです。数字が毎朝勝手に届く状態にすると、横ばいを「横ばい」と認めざるを得なくなります。

### 2. 撤退基準を先に決めた

「1ヶ月計測して有意な変化がなければ降格」「go/no-go の再判定は8月末の1回だけ」と、判断の回数と期日を先に固定しました。これがないと「あと2週間だけ」が無限に続きます。実際、降格の意思決定は当日15分で終わりました。数字が全部揃っていたからです。

### 3. 維持費を極小化する設計にした

維持費が年間約$9(ドメイン代のみ)なので、「完全撤退」ではなく「維持運転」という選択肢を取れました。サーバー費が月数千円かかっていたら、たたむか delusion を続けるかの二択になっていたはずです。**撤退のグラデーションはアーキテクチャで買える**、というのは作る前に知りたかった教訓です。

なお維持運転への降格と同時に、好転(課金発生・検索流入の閾値超え)だけは自動検知して通知が飛ぶ仕掛けを入れました。「見捨てるが、見逃さない」の分離です(この撤退判断の自動化も別記事にします)。

## 無駄だったこと 3つ

### 1. 誰も来ない段階で API課金基盤まで作り込んだ

開発者向け API 課金(Stripe 連携・プラン管理)まで先行実装しました。結果、その導線を通った人は0人です。「課金の受け皿がないと機会損失」という理屈は、**訪問者がいる**サービスにだけ成立します。YAGNI はコードの中だけでなく事業の工程にも効きます。

### 2. 集客を HN / Reddit 頼みで計画した

ローンチ告知の本命を Hacker News と Reddit に置いていましたが、新規アカウント・新規ドメインはスパム判定で構造的に弾かれました(Show HN は投稿が採番すらされませんでした。この顛末は別記事で書きます)。**ゲートキーパー型チャネルは、実績ゼロの新規に最も冷たい**。ここを本命にした計画は最初から破綻していました。

### 3. 「掲載されること」を「配布チャネルを持つこと」と混同した

note に紹介記事を6本書きました(合計スキ4、フォロワー0)。プラットフォームに記事やツールを置くことと、読者・利用者への到達経路を**持っている**ことは別物です。quickconv は最後まで「置いてあるだけ」でした。

## 教訓は2ヶ条に集約される

次に何かを作るときの判定基準として、これだけ残します。

1. **配布チャネルが先に存在すること** — 作ってから探すのではなく、既に読者/利用者に届く経路があるものだけ作る
2. **支払い意思が事前検証できること** — 「同種のものに実際にお金が払われている」市場の実測を先に取る

この2つを満たさないものは、どれだけ技術的に面白くても作らない。quickconv の30日データは、その授業料でした。
